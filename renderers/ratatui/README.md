# renderers/ratatui

Rust renderer (`suite-renderer-ratatui`) that draws the resolved view format as styled [ratatui](https://ratatui.rs) lines, for full-screen terminal apps. It has no terminal, input or scrolling code: the app owns the screen and scrolls over the lines. Conventions shared by all renderers are in `../README.md`.

```rust
use suite_renderer_ratatui::{buttons, render_item, Options, Palette};

let opts = Options { theme: Palette::from_theme(&theme), ..Options::default() };
let lines: Vec<Line<'static>> = render_item(&item, width, &opts);   // wrapped to `width` cells
let actions = buttons(&item);   // label, action, args, key; in drawing order, for arrow-key selection
// press: send ui.action {session, ref: item.ref, action, args}; `copy:` actions: actions[i].copy_text()
```

- `render_item(&ViewItem, width, &Options) -> Vec<Line<'static>>` is pure and does not touch the terminal, so the app can cache the lines per item until the item, the width or the options change. No line is wider than `width` cells (CJK and emoji count by display width, long words are cut, tables and kv are truncated with `…`). Items are not separated: the app puts a blank line between them (or not).
- `Options`: `prose_width: Option<usize>` (prose wraps at most there), `expanded` (tool items: full result instead of the compact form), `show_thoughts`, `preview_lines: Option<usize>` (items with buttons, such as a permission request previewing a diff: the diffs and code above the buttons stop after this many lines with `… N more lines`, unless `expanded`; a blank line separates them from the buttons), `focused_button: Option<usize>` (index into `buttons(item)`; drawn reversed), `theme: Palette`, `images: Option<ImageOptions>` (see Images below), `openui: HashMap<doc id, UiState>` (see OpenUI below).
- **Images.** The renderer cannot draw pixels, but it can leave room for them. With `Options::images` set (`max_rows`, the pixel size of a terminal `cell`, and a `status` per `src`: `Loading`, `Ready {width, height}` or `Failed(why)`), an `image` component whose source is `Ready` becomes blank lines (as many rows as fit the width and `max_rows` at the picture's aspect ratio, never larger than its natural size; `image_cells` does the arithmetic) followed by a muted `alt · W×H` caption. `render_item_images(&item, width, &opts)` returns those lines together with `images: Vec<ImageSlot>` (`line` within the item, `x` column, `cols`, `rows`, `src`): the app draws the pictures over the blank lines after the text, so slots survive any nesting (card gutters, the `⎿` elbow, indents). `Loading` is `[image alt] loading image…`, `Failed` is `[image alt · why]`, and without `images` it is the plain `[image alt · W×H]` placeholder. In a compact tool result the picture is shown beside the text and does not count against its three lines. `image_sources(&item)` lists the sources an app has to look at.
- `Palette` is the daemon's `Theme` colors as `Color::Rgb` (`Palette::from_theme`, `Default` = `protocol/themes/default.json`). Fields are public: map them to 16/256 colors or `Color::Reset` for `NO_COLOR`. Plain text has no foreground color of its own, so the terminal's is used.
- Untrusted text is cleaned before it is drawn: control characters (escape sequences in tool output) and bidi overrides are dropped, tabs expand to 4-column stops.

## OpenUI

`openui` components and `openui` blocks in text (`docs/openui.md`) are drawn from the evaluated `UiDoc`: the renderer never parses OpenUI Lang or holds `$state`. Everything purely visual comes in through `Options::openui`, a `UiState` per doc id (it is pure, the app owns the state): `focus` (the focused target), `tabs` (selected tab per `Tabs`), `open` (accordion items opened or closed by hand), `edits` (a text field's `UiEdit {text, cursor}`, drawn instead of the node's `value` with the cursor as a reversed cell), `values` (what was chosen here and the daemon has not echoed yet) and `select` (the open `Select` list and its highlighted option).

```rust
let targets = openui_targets(&item, &opts);   // fields and buttons by key, tabs and accordion items by path
let docs = openui_docs(&item);                // per doc: id, streaming, interactive (has keys), focusable
let r = render_item_images(&item, width, &opts);   // r.focus_line: first line of the focused target
```

`openui_targets` lists what can take focus in drawing order (docs in document order). It depends on the state, because a tab that is not selected and a closed accordion item draw nothing. A target has the doc id, an `id` (the node's `key`; for `Tabs` and `AccordionItem` the node path in the doc, `/children.2` or `/items.0`, which the state maps are keyed by too), its `kind` (with the options of a select, the range of a slider, the `url`/`copy`/`disabled` of a button), a label, the daemon's `value` and the `form` it sits in. A `streaming` doc draws but has no targets.

- **Layout.** A `row` Stack measures its children: each at its preferred width with the gap between (`none` 0, `s` 2, `m` 3, `l` 5 cells), squeezed towards the minimum when it does not fit (text breaks at words, a metric, tag or button keeps its width), wrapped onto further lines with `wrap`, else stacked. `justify` and `align` place the rest. A column Stack follows `gap` (`l` is a blank line) and `align`. `Tabs`: `│ One │ Two │` with the selected one reversed (accent and bold while focused; a strip wider than the view scrolls), over the selected tab. `Accordion`: `▸ title` / `▾ title` and the children indented. `Steps`: `✓ ● ○ ✗` by status, the detail muted.
- **Grid and auto-layout.** `Grid` puts its children in as many columns as fit at 36 cells each (at most `columns`), left to right then down, one cell between columns; the columns share the width evenly, and every `Card` in a row is stretched to the row's tallest, so the outline bottoms line up (other children keep their height; a row with something other than cards is separated from the next by a blank line). One column when narrow. The same happens without a `Grid`: in a column Stack, `Card`, `Tab` or `AccordionItem`, a run of two or more sibling `Card`s is drawn as a grid and a run of two or more `Metric`s as a strip. Siblings of other kinds between them end a run, and a row Stack is never regrouped (except that a row of only Metrics is a strip).
- **Cards** float: `╭─ title ─╮ │ … │ ╰─╯` in the border color (the `tone` colors outline and title), the whole box, outline included, on the palette's `surface`, one cell of padding inside. Inside a card, spans that have a background of their own keep it and reversed (focused) spans stay reversed, so a focused button still stands out. A card in a card sits on the same surface; its outline tells it apart. `sunk` is the fill and padding without the outline, `clear` neither (the title bold above the children). Below 6 cells wide a card has no frame.
- **Metrics.** A metric strip puts each `Metric` in a column: value in bold with the `delta` after it in the tone's color, the label muted under them; columns are divided by `│` (two spaces each side when the strip fits one line with them, one otherwise) and wrap onto further strips, a blank line between. A lone Metric is the same column.
- **Progress** is `▰▰▰▱▱▱ 60% label`; when the label already says the percent (`92% used`, a `%` number that rounds to the bar's), it is not printed twice. The bar is at most 40 cells and goes over its text when it would keep fewer than ten.
- **Content.** `Text` and `Callout` draw their `blocks` (a `┃ ` gutter in the tone, the title bold); `Code`, `Image` and `Link` are the existing code, image and link drawing. `Table` cells may be nodes (`Tag`, `Link`, `Text`), numbers align right. `Tag` is `[label]` in its tone. `Table` is a bold header, a rule and the rows, with no blank line between.
- **Charts** by meaning: `BarChart` as columns of `▁…█` with a value axis, series side by side or stacked, or as bars lying down (when `horizontal` or when the labels do not fit under columns): muted labels left, then `▄▄▄▖` half-height bars in half-cell steps (the upper half of the line stays empty, so bars on neighbouring lines never merge), the value at the bar's end; `LineChart` and `AreaChart` on a braille canvas with a value axis, the labels at the foot and a legend; `PieChart` and donut as one stacked bar and `■ label  42%` lines; `Sparkline` as `▁…█` and the last value. Series are colored accent, success, danger and mixes of them.
- **Forms.** An input is `Label *` over `[ value or placeholder ]` (up to 44 cells wide), the error under it in the danger tone, the hint muted. `TextArea` takes at least three rows; `Select` shows the choice and `▾` and, while `state.select` names it, its options under it; `RadioGroup` `(•)`/`( )`; `CheckBox` `[x]`/`[ ]`; `Switch` `● on`/`○ off`; `Slider` a bar with the number and the range; `DatePicker` a text field with the `YYYY-MM-DD` placeholder that turns danger when it holds something else. `Button` is `[ Label ]` (`primary` accent, `danger` red, `disabled` dim, `↗` for a `url`, `⧉` for `copy`), reversed while focused.
- Unknown components are a muted `[unsupported: Name]`; a partial node draws what it has; a doc without a root shows `[ui: <first error>]` or nothing.
- **Compact results.** An `openui` tool result is its first title and `… +N lines`. A doc with fields or buttons, and a doc that holds focus, is always drawn in full, like an item with buttons.

## How items look

| kind      | Drawn as                                                                                                                                                                                                                                  |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user`    | `> text` (prompt in accent, text hangs under it); the app it came from dimmed after the text (`> make it smaller  · browser`)                                                                                                             |
| `agent`   | the text; a guest's label as a small accent header line                                                                                                                                                                                   |
| `thought` | `∴ thinking` (muted); with `show_thoughts` the text in muted italic after `∴ `                                                                                                                                                            |
| `tool`    | `● label` (bullet: running accent, failed danger, else muted, so failures stand out; the verb bold, what it acts on not: `read` src/a.rs), then the result: compact and muted under `⎿ `, or the whole component indented with `expanded` |
| `notice`  | the text in muted (danger when failed)                                                                                                                                                                                                    |

This deliberately differs from the shared item conventions (`» label` header, `✓`/`✗` state glyphs, `… thinking`) in favour of a quieter, denser look; the structure and the buttons behave the same.

**Compact tool results** are one line: the first line of the first leaf (card title, text, code, diff, ...), and what was left out counted at its end, `… +N lines` (on a line of its own when too narrow). Code: its first line, cut to the width. Diff: `path  +3 −1`. Kv: `k: v · k: v` (a value with a `tone` in its color, bold). Table: `3 rows · name, size`. Image: `[image alt]`. Everything short (file, link, progress) as it is. **Items that contain buttons are always drawn in full**: the buttons are what they are for (permission requests, choices).

**Components**: `card` is a `╭ title` line and a `│ ` gutter (tone colors both); `row` puts children side by side only when each is one line and they all fit, else stacks them; `stack` gap `l` is one blank line, `s`/`m` none; `text` blocks as in the Go TUI (headings bold, levels 1 and 2 in accent, never underlined (that is a link); with `prose_width` set, paragraphs, headings and lists wrap there however wide the item; markdown tables in a `┌─┬─┐` box, cells wrapped inside their column, aligned as the separator row says, rules between rows once one wraps, and `header: cell` lines per row when too narrow for the box; `•`/`1.`/`[x]`, `│ ` quotes, rules, inline code on the surface color, links accent+underline with the URL after them); `code` on the surface color with the band filling the width (shell highlighted; a `code` component in `bash` also breaks lines too long after `&&`, `||`, `|` and `;`, outside quotes, `$(…)` and heredocs: a command to approve); `diff` colored `+`/`-` lines with muted hunk headers; `table` columns separated by `│` under a rule, widest columns cut first; `progress` `▓▓▓░░ 60% label`; `button` `[k Label]`; `image` `[image alt · W×H]` (or room for the picture the app draws, see Images); `file` `📄 path`. Unknown components and blocks (a newer protocol) draw a muted `[unsupported: type]` placeholder.

## Tests

`cargo test -p suite-renderer-ratatui`. Every `fixtures/<name>/resolved.json` is drawn and compared with `ratatui.txt` (80 columns), `ratatui-40.txt`, `ratatui-expanded.txt` (tool results in full, thoughts shown) and `ratatui-styled.txt` (every styled run as `⟦style|text⟧`, colors by theme name) next to it; `UPDATE_SNAPSHOTS=1` rewrites them. A sweep checks that no line of any fixture is wider than the width, from 1 to 200 columns. `tests/behavior.rs` covers wrapping, compact summaries, `buttons()`, focus, unknown components and narrow widths; `tests/openui.rs` the OpenUI drawing (row layout, charts, forms, focus targets, tabs, narrow widths). Everything is headless: lines are inspected as data, nothing opens a terminal.
